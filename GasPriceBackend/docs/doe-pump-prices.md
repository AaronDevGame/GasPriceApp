# DOE pump prices

## Extraction benchmark

`POST /admin/fuel-prices/doe/benchmark` accepts `{"sourceUrl":"https://doe.gov.ph/path/to/report.pdf"}` with `Authorization: Bearer <ADMIN_API_KEY>` and `Content-Type: application/json`. Only `sourceUrl` is accepted. Use a direct PDF link from the DOE listing, not the listing page itself.

This synchronous diagnostic downloads the PDF once and runs two independent paths with the configured `OPENAI_MODEL` (default `gpt-5.6-luna`): the existing page-by-page AI extractor, then local table extraction with AI fallback for unsupported or ambiguous pages. Set `OPENAI_MODEL=gpt-6-luna` in the server configuration to benchmark Luna; the endpoint does not change the production model. Both runs bypass persisted extraction caches. It neither reads nor writes the production price/report/page-cache tables and does not enqueue an import job.

The experimental local parser currently supports embedded-text NCR tables with the standard ordered company columns, seven fuel grades per city, and explicit coverage dates (or dates from a previously parsed local continuation page). It uses PDF word coordinates to preserve columns, ignores independent/overall/common-price columns, and falls back for scanned PDFs, other regional layouts, incomplete blocks, and ambiguous price pairs. This is an initial benchmark parser, not a guarantee of complete or accurate extraction.

The response uses the usual `ApiResponse` envelope. `data.ai` and `data.hybrid` contain status, error, elapsed milliseconds, model, token usage, estimated cost, AI request count (including retries), extracted dates/rows, and page validation progress. `hybrid.localPages` records each local attempt, accepted row count, and fallback reason. Timing covers extraction, validation, and retries; `downloadMilliseconds` is separate. Partial/failed runs remain visible with their available billing; unknown usage/cost stays null. A local-only run makes zero AI calls and has zero API spend even though usage and estimatedCost are null.

`data.comparison` contains matching rows, date agreement, rows missing/different on either side, and estimated API savings in USD (AI minus hybrid; negative means hybrid cost more). A failed run has no comparison. Agreement measures consistency, not correctness: compare the outputs against manually checked PDF rows. Estimates exclude backend CPU/hosting, use standard token rates for supported models, and do not establish production savings until tested on representative reports. Failed upstream calls with unavailable usage leave the total cost unknown.

Requests are capped at 12 MB and four PDF pages before paid extraction starts, with a ten-minute overall timeout, one benchmark at a time per server process, and a 30-second cooldown using the shared admin rate-limit bucket. This endpoint makes real billable AI requests even for an already imported report. Keep the HTTP connection open; reverse proxies may have shorter timeouts. A timed-out or disconnected request may incur AI usage without delivering a final report. Larger production imports continue to use the existing durable job API.

Run offline checks (fake AI, no production database):

```bash
dotnet run --project GasPriceBackend/tests/DoeBenchmarkChecks
# Optional: also check a downloaded NCR report locally, without sending it to AI.
dotnet run --project GasPriceBackend/tests/DoeBenchmarkChecks -- /absolute/path/to/ncr-report.pdf
```

`POST /ai/fuel-prices` resolves coordinates and checks fresh DOE city/company pump prices before reusing a research cache or checking the configured direct websites and AI web search. The DOE source is the regional weekly PDF linked from [Retail Pump Prices](https://doe.gov.ph/data-and-prices/liquid-fuels/retail-pump-prices). DOE rows represent a company price or company price range for a city and fuel grade. They do not identify a physical station.

When DOE supplies the research result, `model` is `direct:doe`, `source_tier` is `government`, and the response includes `doePrices` with the individual company rows. Other research responses have `doePrices: null`. The existing area estimate fields remain available. A DOE import can use OpenAI to read the PDF; the `usage` and `estimatedCost` fields in this response do not include that extraction call.

Location matching requires the same province (including known names such as NCR/Metro Manila) and an unambiguous city or municipality. Accents and printed forms such as `Imus City`, `City of Imus`, and `Imus` can match within that province; company rows using those forms are combined for the newest report week, with an exact locality name preferred for duplicate company/grade rows. Quezon City in Metro Manila never matches a locality in Quezon province. If Geoapify omits the region, the province selects the DOE regional report. Conflicting known province and region values do not produce a DOE match. DOE import failures still fall through to the configured website and AI sources; a `direct:*` website model with `doePrices: null` does not by itself identify which DOE step failed.

`GET /fuel-prices/doe?latitude=14.6&longitude=121.0` requires the same player authentication as other fuel-price endpoints. It resolves coordinates, returns the latest fresh rows for the city and province, and attempts a DOE import if none are stored. If DOE has no matching current rows or cannot be read, it returns an empty `prices` array. The endpoint does not return website or AI estimates. A DOE report qualifies until seven days after the report's week end; a current-week report uses its Tuesday start as the estimate date, while a completed report uses its Monday end. The API needs `GEOAPIFY_API_KEY` to resolve coordinates and `OPENAI_API_KEY` for a new PDF extraction.

`POST /admin/fuel-prices/doe/import` accepts JSON `{"city":"Quezon City","province":"Metro Manila","region":"National Capital Region"}` and the admin bearer key. Optional `sourceUrl` selects a DOE PDF explicitly. Without it, the backend finds the newest recent PDF on the matching regional page. The importer extracts only the requested city/province, validates the report week, companies, grades, ranges, and duplicate cells, and upserts matching rows. It now returns HTTP `202 Accepted` with `data.jobId`, `data.statusUrl`, and a matching `Location` header immediately after persisting the job. Poll `GET /admin/fuel-prices/doe/import/jobs/{jobId}` with the admin bearer key until the job reaches a terminal state. Polling includes `request` (city, province, optional region and sourceUrl), live report progress when available, and `result` containing the former synchronous response (`imported`, `updated`, or `already_imported`). Before completion, `result` is null. This changes the previous synchronous response contract; clients must poll for the final result. Admin imports can use older PDFs by supplying `sourceUrl`; the public feed still returns only recent rows.

For a manual whole-report import, send only `{"sourceUrl":"https://doe.gov.ph/path/to/report.pdf"}` to the same endpoint. No city, province, or region is required: the importer counts pages locally, sends each page separately to the extractor, validates and upserts company prices only after every page succeeds, records a complete report, and expires affected research caches. The accepted response supplies the job ID and polling URL. Polling exposes live page progress and, on completion, `data.result` contains `sourceUrl`, `status`, `added`, `updated`, `priceRows`, duplicate/aggregate counts, extraction usage/cost, and final `pageProgress`. Repeating the request reuses clean cached pages for identical PDF content and extraction settings; unchanged complete reports return `already_imported`. To import only one locality, supply both city and province, with optional region and sourceUrl as above. Partial location fields are rejected; city-only extraction remains a single whole-PDF request.

This import endpoint does not accept `from` or `to`. Use the bulk backfill job for a date range.

`GET /fuel-prices/doe/browse` is an authenticated, read-only feed for the Fuel Prices tab. It lists cities and municipalities with a recent stored report and includes the latest week of company prices for the first listed location. Add `?city=Quezon%20City&province=Metro%20Manila` to select a listed location. Both filters must be supplied together. It reads stored rows only; it does not geocode or import a PDF. A report qualifies if its week has started and its end is no more than seven Philippine calendar days old. The feed can be empty when no recent report has been imported.

`POST /admin/fuel-prices/doe/import/jobs` starts a bulk import with `{"mode":"latest"}` or an inclusive historical backfill such as `{"mode":"backfill","from":"2026-09-01","to":"2026-09-30"}`. A backfill request is limited to 91 calendar days; larger archives should be imported in consecutive ranges. The endpoint returns `202` and a job ID. Poll `GET /admin/fuel-prices/doe/import/jobs/{jobId}` for per-PDF results, counts, and errors. Both POST routes share one persistent queue: requests can be submitted together, and one import runs at a time in creation order. Additional bulk submissions are queued rather than rejected while another import is active. Automatic latest-data scheduling is currently paused by default to save extraction tokens (`DoeImport:ScheduleEnabled` is `false`). To resume, set `DoeImport__ScheduleEnabled=true` in the backend environment and restart or redeploy; the server then starts a latest-data job roughly every six hours while it is running. This setting only controls creation of scheduled jobs: manual imports and already queued jobs still run, and on-demand city extraction remains available. This in-process schedule does not run while the host is asleep or stopped.

While a PDF is being extracted, its entry in `reports` has `status: "running"`. Its `pageProgress` is saved before and after each page, including the job heartbeat, so polling can show progress before that PDF finishes:

```json
{
  "status": "running",
  "pageProgress": {
    "pagesTotal": 19,
    "pagesCompleted": 3,
    "currentPage": 4,
    "pagesFailed": 0,
    "pages": [
      { "pageNumber": 1, "status": "completed", "attempts": 1, "priceRows": 34, "error": null },
      { "pageNumber": 2, "status": "completed", "attempts": 1, "priceRows": 41, "error": null },
      { "pageNumber": 3, "status": "completed", "attempts": 1, "priceRows": 19, "error": null },
      { "pageNumber": 4, "status": "running", "attempts": 1, "priceRows": 0, "error": null }
    ]
  }
}
```

This example omits queued entries for pages 5–19; actual responses include every counted page. `pagesCompleted` counts successfully read pages, including readable pages with zero eligible company prices or individual skipped cells. `currentPage` is the page currently being extracted or retried, and is null between pages and after extraction. Page statuses are `queued`, `running`, `retrying`, `completed`, `completed_with_errors`, or `failed`; `priceRows` counts validated company rows on that page, not database inserts. INDEPENDENT, OVERALL RANGE, and COMMON PRICE remain excluded. A failed page is retried once without re-extracting earlier successful pages; remaining pages are still attempted. If any page remains unreadable or has invalid dates/structure, no prices from that report are saved, its result is `failed`, and the job finishes with gaps. All extraction requests, including readable billed failure/retry responses, contribute to report and job usage/cost.

Each page extraction also returns its actually printed company/summary column labels in order. The backend passes those labels as context to subsequent continuation pages that omit headers, without making a separate AI request. New printed headers override the previous table's mapping; context is cleared after an unreadable page. Company identity or column alignment that remains ambiguous still fails the page rather than inventing a company. Previously verified report dates can likewise supply missing dates on continuation pages.

Valid range endpoints are sorted before deduplication and saving: `77.84–77.50` becomes `77.50–77.84`. Both endpoints must still be PHP 1–300 with at most two decimal places. Values are never rounded, clamped, or guessed to make them pass. A readable page with invalid individual rows continues using its valid rows and has `status: "completed_with_errors"`, `cellErrors`, and a summary `error`. Each cell error identifies the extracted row, city, province, company, grade, and reason. Conflicting versions of the same company/grade cell are all skipped rather than choosing a winner. Page `duplicatesIgnored` and `aggregateRowsIgnored` distinguish ignored repetitions/summary cells from invalid rows.

When all pages were readable but some rows were skipped, valid prices are saved, the report result and stored report have `status: "partial"`, and the job finishes `completed_with_gaps`. Both manual job results and job report entries include `rowsSkipped`; per-page diagnostics are under `pageProgress.pages[].cellErrors`, and cross-page conflicts are under `rowErrors`. These reports are counted in `reportsFailed` rather than clean imports, even though `priceRowsAdded` and `priceRowsUpdated` record successful saves. Existing saved prices for skipped cells are left intact. Partial reports must not be treated as verified complete imports for any future hash-based skip optimization.

Progress is persisted in the existing job details JSON. Older job results have `pageProgress: null`. The `AddDoePageCache` migration adds `doe_page_cache`, which stores each clean page extraction immediately, before the report price transaction. A new job or process restart can reuse those results and retry only missing pages. Cache keys include the whole PDF content hash, page number, extraction instruction/schema version, configured model, and listing context. Cached payloads are revalidated, and their dates and ordered table headers are restored for continuation pages. Readable empty or independent-only pages are cached too; pages with skipped cells are not. If PDF content or extraction rules change, old results are not mixed into the new extraction. No existing report prices are removed. PDFs are bounded to 100 pages in addition to the existing download size limit.

Bulk imports discover every PDF on the five DOE report pages for the selected week or range, including the newest PDF for each South Luzon subdivision. Each PDF is extracted for all clearly identified localities and upserted into `doe_fuel_price`. `doe_pump_price_report` records the source section, subdivision, dates, URL, content hash, and row count; `doe_import_job` retains job progress. Existing city imports are linked to partial legacy report records by the migration. Successful bulk imports mark a report complete. Missing or stale latest report groups appear as job gaps. When new rows arrive, affected research cache entries are expired so subsequent location requests use the stored DOE rows. Both latest and backfill jobs download the source PDF to check its content hash, reuse clean cached page results, and extract only missing or invalid pages. Revised PDFs or extraction settings require new extraction. Reports imported before the page cache was introduced need one extraction to populate it; existing report status alone is not proof of a usable page cache.

An `already_imported` report means validated extraction results, whether newly read or cached, found no database changes. Previously saved prices remain when a later extraction omits them. Bulk upserts match existing rows across the same city and province aliases used for reads, then add only missing company and fuel-grade rows. `priceRowsAdded` counts physical inserts across all PDFs in the job; existing duplicate rows are retained. Extracted rows repeated identically by the PDF parser and aggregate columns are ignored; each report result includes `duplicatesIgnored` and `aggregateRowsIgnored`. NCR rows use Metro Manila and National Capital Region as their canonical province and region. Individual invalid or conflicting rows are skipped and reported as described above; unreadable pages and invalid report dates still fail the report. Failed or partial reports are retried by the next latest import.

`GET /admin/fuel-prices/doe/history` reads stored company price rows, newest first. It accepts optional `from`, `to`, `city`, `province`, `region`, and DOE `section` filters, plus `limit` (1–500, default 100) and an opaque `cursor` returned as `nextCursor`. Date filters match report coverage that overlaps the inclusive range. The endpoint returns only imported data; a backfill job is needed for earlier reports. Like all admin routes, these endpoints require `ADMIN_API_KEY`.

DOE reports and PDFs can change format. An unreadable or ambiguous extraction is rejected or falls through to the existing sources. Compare imported prices with the linked PDF before relying on them; the PDF extraction is not guaranteed to copy every cell correctly. Locations absent from a DOE PDF continue through the existing fallback. A new or not-yet-imported locality can still trigger an on-demand PDF extraction and add latency and OpenAI cost.

DOE city import responses include `model`, `usage`, and `estimatedCost`, using the same token and USD estimate contracts as `/ai/fuel-prices`. A city import that skips extraction returns null billing fields. Bulk job status includes these fields for each PDF and aggregate `usage` and `estimatedCost` for recorded extraction responses, including report failures after a readable AI response. The queued response has null totals until usage is recorded. Usage is saved in the existing job details JSON and survives restarts; historical jobs have null totals. Missing provider usage, unsupported model pricing, or mixed pricing rates can make totals unavailable; per-PDF values remain available. Estimates reuse the existing backend pricing table, with zero web-search calls for PDF extraction, and are not billing invoices. Requests that time out or return an unreadable response cannot report their provider usage.

Run the focused page-import checks from the repository root with `dotnet run --project GasPriceBackend/tests/DoePageImportChecks`. Optionally append `-- /path/to/report.pdf` to exercise splitting a real multi-page PDF. These checks simulate the extraction service without paid AI calls or production database access. Set `DOE_TEST_PGPORT` only for a disposable localhost PostgreSQL cluster to also exercise authenticated HTTP job polling and queued manual imports against `gasprice_doe_page_test`; those optional checks apply existing migrations to that test database and retain normal admin rate limits.

Page progress includes `cached: true` and `attempts: 0` on a reused page, plus `pageProgress.pagesCached` for the report. Cached pages count toward `pagesCompleted`. Usage and estimated cost describe only new extraction responses in the current run; a report served entirely from the page cache has null model/usage/cost fields because no new AI call was made. Historical costs are not charged or added again. Cached extraction results are separate from saved public prices, so rebuilding missing price rows from a complete cache also needs no AI calls.

Manual jobs use `mode: "location"` or `mode: "report"`; bulk jobs retain `latest` and `backfill`. Completed manual jobs retain their original import result under `data.result`, while `data.reports` provides the shared counts, usage, errors, and (for whole-PDF imports) live page progress. City imports expose running/final status without page counts because their extractor processes the entire PDF. Terminal job states are `completed`, `completed_with_gaps`, `failed`, and `interrupted`. Queued jobs survive restarts; stale running jobs are marked interrupted after 30 minutes without a heartbeat and must be resubmitted. A periodic heartbeat keeps long manual extractions from being classified as stale. The `AddDoeSingleImportJobs` migration adds nullable JSON request/result columns without changing existing job records.
